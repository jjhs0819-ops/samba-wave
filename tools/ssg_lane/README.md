# SSG 추가 레인

SSG 수집 처리량을 늘리기 위해, 주거용 프록시 IP 하나당 브라우저 하나를 더 띄우는 도구.

## 왜 이렇게 하나

SSG 는 Akamai 봇 보호가 걸려 있어 **실제 브라우저만 통과**한다. 2026-08-06 실측:

| 방식 | 결과 |
|------|------|
| 백엔드 httpx + 주거용 프록시 3개 | 전부 403 |
| 백엔드 httpx + 집 IP | 403 |
| curl_cffi (크롬 TLS 지문 위장) + 프록시 | 전부 403 |
| **실제 크롬 + 같은 프록시 IP** | **200 정상** |

같은 IP인데 브라우저면 되고 프로그램이면 안 된다. 즉 **IP 가 아니라 브라우저 여부**가
관문이라, 무신사·롯데온처럼 백엔드에서 프록시만 돌리는 방식은 SSG 에 쓸 수 없다.

크롬의 프록시 설정은 **프로세스 단위**라 IP 를 나누려면 인스턴스를 나눠야 한다.
프로필만 나누는 것으로는 안 된다.

## 로컬 중계기(proxy_relay.py)가 필요한 이유

- 크롬 `--proxy-server` 는 URL 에 넣은 `id:pw` 를 무시하고 **인증창을 띄운다**
- MV3 확장앱은 blocking webRequest 가 막혀 `onAuthRequired` 자동응답이 불가

그래서 인증 없는 로컬 프록시를 열고, 상위 프록시로 넘길 때만 `Proxy-Authorization`
헤더를 붙인다.

**중요**: 중계기는 CONNECT 를 그대로 relay 만 하고 **TLS 를 절대 복호화하지 않는다.**
mitmproxy 처럼 TLS 를 풀었다 다시 맺으면 지문이 바뀌어 SSG 가 차단한다.

## 사용법

```powershell
powershell -File tools/ssg_lane/start_ssg_lane.ps1
```

기본값은 중계 포트 18101 / CDP 9401 / 상위 프록시 `119.206.200.126:6014`.
레인을 더 늘리려면 포트와 상위 프록시를 바꿔 실행한다.

```powershell
powershell -File tools/ssg_lane/start_ssg_lane.ps1 -RelayPort 18102 -DebugPort 9402 -Upstream 119.206.198.137:6014
```

## 최초 1회 설정

브라우저가 뜨면 확장앱이 새 `deviceId` 를 만든다. 그 상태로는 잡이 가지 않는다.

1. 확장앱 팝업에서 백엔드 주소(`https://api.samba-wave.co.kr`)와 키 입력
2. SSG 체크
3. **서버 분담 설정에 그 deviceId 를 SSG 로 배정** — 배정은 서버 값이 권한을 가지므로
   확장앱 로컬 체크만으로는 잡이 발행되지 않는다

## 주의

- 레인 1개당 메모리 약 830MB (이미지·GPU 끈 상태). 여유 메모리를 보고 늘릴 것
- SSG 동시성은 1 을 유지한다. 올려도 빨라지지 않고 차단만 늘었다(2026-08-06 실측:
  동시 1 → 40건 475초/실패 0, 동시 3 → 40건 496초/실패 3·백오프 2회)
- 차단은 요청 강도에 비례해 길어진다. 30건 몰아치기 시 20분 넘게 403 지속
